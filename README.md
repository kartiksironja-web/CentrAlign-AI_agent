## 1. What this is

Give VerifyOps one sentence, such as "Enter Acme Supplies' latest invoice into the ERP and tell me when it's done." It reads the company handbook, works out what to do, operates a real browser and a real API in a sandboxed mock company, and returns a report with evidence.

The point of the project: most agents end with "Done!" as the model's own opinion. In VerifyOps, "done" is only accepted after an independent, non-LLM auditor checks the actual system state. I also measure how often an agent claims success when the result is wrong.

**Core principle: the LLM proposes, code disposes.**

The LLM decides what the request means, which tool to use next and how to recover. Plain code decides whether an action is permitted (policy gate), whether the task succeeded (auditor), when to stop (budgets) and what gets logged.

## 2. Architecture (short)

```
 request ─► Understand ─► Pick SOPs ─► Plan ─► WORKER LOOP ─► AUDITOR ─► report + run.json
             (LLM)         (LLM)       (LLM)   observe→reason→act   (plain code)
                                                 │      ▲              │ fail: hint, retry (max 2)
                            every write ─► POLICY GATE (code)           │ then escalate to human
                                                 │   + detectors (code)
                                                 ▼
                      Browser · HTTP API · Documents · Notes · Human
                                                 │
                        apps/company  (mock portal + ERP, SQLite)
                                                 ▲
                                                 └── auditor reads it READ-ONLY (separate channel)
```

| Part | Who decides | Where |
|---|---|---|
| Understand the request, pick SOPs, plan | LLM | `agent/contract.py`, `agent/loop.py` |
| Choose next tool and recover from surprises | LLM | `agent/loop.py` |
| Allowed / needs approval / forbidden | **Code** | `agent/gate.py`, `company_pack/policy.yaml` |
| Detect no-ops, errors, loops, wrong page | **Code** | `agent/detectors.py` |
| Was it actually done? | **Code** | `auditor/` |
| Company knowledge (rules, systems, limits) | **Data** | `company_pack/` |

**Handbook, not scripts.** The company knowledge is in markdown SOPs containing rules and a "definition of done", never click-paths. The agent finds its own way through the UI.

## 3. How one run works

1. **Understand:** the request becomes a structured task contract (goal, entities, ambiguities). If the model reports an ambiguity, code allows nothing but asking the requester until it has. Whether the model *notices* an ambiguity is up to the model: in scenario S2 (two similar vendors) it did not ask, in any run (section 7).
2. **Handbook:** the LLM selects relevant SOPs from their titles and summaries.
3. **Plan:** a short checklist; every re-plan is logged with a reason.
4. **Act loop:** each step the model sees structured state (not an ever-growing chat), returns **one** tool call with a stated reason, the gate checks writes, the tool runs, detectors inspect the result.
5. **Self-check:** after writing, the agent re-reads the saved record.
6. **Declare assertions:** the agent states what must be true, as data.
7. **Audit:** the auditor compares the declared facts against the databases and against an independent source, and checks that nothing else changed. Failure goes back to the agent with a hint (max 2 rounds), then escalates to a human.
8. **Report:** outcome, evidence, anything needing attention, run id.

A real run explained step by step is in `docs/AGENT_WALKTHROUGH.md`. Design decisions, with the alternatives I rejected, are in `docs/DECISIONS_LOG.md`.

## 5. The mock company and injected faults

One small FastAPI app serves a **vendor portal** (invoice list and PDFs) and an **internal ERP** (forms and a JSON API). Faults are switchable and **off by default**. They are *test conditions I created on purpose*; the agent is never told about them.

| Fault | What it simulates |
|---|---|
| `DATE_TRAP` | ERP silently reads `03/11/2026` as 11 March instead of 3 November and still shows "Bill saved" |
| `SAVE_BROKEN` | The Save button does nothing |
| `BUTTON_RENAME` | The Save button's label and id change |
| `DUPLICATE_VENDOR` | Two similarly named vendors exist |

(A `SESSION_EXPIRY` fault was planned as a low-priority extra and is **not built**.)

### Reading the tables

- **Where it works.** S1 (the happy path) 3 of 3. S5-deny 3 of 3: a refused approval was respected, nothing was written, the run handed over as `needs_human`. S5-approve and S4 (a dead Save button; the agent switched to the API) each 2 of 3. Mark-a-bill-paid 3 of 3 and onboarding a vendor 2 of 3, on code that did not change.
- **Where it does not.** S2 (two similar vendors): the right vendor and data in 3 of 3 runs, but the agent **never asked** the human first, so "meets expectations" is 0 of 3. S3 (a silent date fault): 1 of 3 verified with the audit enforced (2 of 3 if the re-run replaces the run that died) and 1 of 3 with it advisory; in advisory mode one run claimed success on a wrong date and the wrong value stood (a false completion). The revision update (S6) ends with the bill correct in 3 of 3 runs after the fix, but none of them verified: two ran out of steps and one handed over as `blocked`.
- **The auditor's blind spot is measured, not hidden.** "Auditor false pass" counts runs the audit passed while the harness's independent ground-truth check (not the auditor) says the result is wrong: S5-approve 1 of 3 (an older invoice was chosen and the checks agreed with that choice) and S6 first batch 3 of 3. The audit verifies the saved record against the source the agent cites; it cannot know the source was the wrong one. Both runs are in `runs/samples/`.
- **Audit enforced versus advisory (S3)** is in `evals/RESULTS.md`: with only 3 runs each, this repository cannot say that enforcing the audit helped. The honest reading is "no measurable difference at this sample size".
- **Cost and time.** All 21 runs of the main sweep cost about $0.54 at list price (the plan used was free) and took 59 minutes of run time; a run is 2 to 5 minutes because model calls are spaced out for the free plan.
- **Not independent of my tuning.** About 40 development and pilot runs (14 single runs and five pilot batches totalling 26 runs) used these same tasks with fixes in between, and the handbook was edited after seeing failures (decisions #77 to #97 in `docs/DECISIONS_LOG.md`, `docs/PROGRESS.md`). The new tasks were not run before the freeze, but S6 was tuned after its first batch (disclosed above).

## 8. What is autonomous and what is hard-coded

**Autonomous (decided by the model at run time):** interpreting the request; choosing which SOPs apply; planning and re-planning; choosing between UI and API; navigating pages it has never seen scripted; extracting values from documents; noticing a wrong saved value and trying another way to enter it (seen in S3: one run repaired it by itself, others did not); switching to the API when a button is dead (S4: 2 of 3 runs); deciding when to ask a human. **Honest evidence on the last two points:** the sweep recorded no repair that the *auditor's* feedback caused (0 of 21), and in S2 the model never asked the human first.

**Code-enforced (deliberately *not* autonomous):** permissions and approval limits; success verification; retry budgets and stop conditions; logging.

**Hard-coded or manually configured:** the loop and tool interfaces; the mock apps and fault flags; SOPs, policy and connector manifests (data files I wrote, including the approval limits of 50,000 rupees and 60 days of payment terms); the "Where the truth is" section of each SOP, which tells the agent which document lines and tables are the independent sources for its checks (without it the small model could not write valid checks); the step, time and cost budgets (60 steps, 600 s, $1 per run) and the spacing between model calls; the scripted "human" answers used in evals (labeled `SCRIPTED_HUMAN`); model choice via `.env`.

## 10. Assumptions

- The company exposes a **read-only view of the systems it operates** so verification is possible. (True in my sandbox; often not true in real enterprises.)
- SOPs are written as rules plus a "definition of done" plus a "where the truth is" note naming the independent sources. Verification quality depends on this; the handbook contains no real values from the data, and a test enforces that (`tests/test_handbook_has_no_answers.py`).
- The requester is reachable for clarification and approval. In evals this is scripted and labeled.
- Single task at a time, single user, single tenant, English-language documents.
- Dates in documents follow Indian convention (DD/MM/YYYY).
- The model supports tool calling.

## 11. Known limitations

(Details and mitigations in `docs/LIMITATIONS_AND_FUTURE.md`.)

1. **The auditor can agree with a wrong choice.** It checks the saved record against the source *the agent* cites. Measured: in S5-approve one run picked an older invoice and the audit passed; in the first S6 batch the agent changed nothing, cited the original document, and the audit passed three times. The harness's independent ground-truth check caught both ("Auditor false pass" column). A handbook-only fix helped the data but exceeded what the small model could write within its budget.
2. **The model does not reliably ask when it should.** In S2 it chose the right vendor in 3 of 3 runs and never asked first (0 of 3 meet the expectation).
3. **The agent writes its own assertions**, the hardest part for a small model. Code enforces coverage of fields the SOP requires and independent sources, but the handbook has to say where the truth is, and a vague handbook means weak checks.
4. **One small model on a free plan, 3 runs per scenario.** One run moves a rate by 33 points; the same task ended differently from run to run. Temperature was left at the provider's default.
5. **The evaluation is not independent of my tuning.** About 40 development and pilot runs used the same tasks as S1 to S5 with fixes in between (`docs/PROGRESS.md`); a handbook example once leaked real values and the affected runs were discarded.
6. **The auditor needs read access to the target system.** Fine in a sandbox; not guaranteed in production.
7. **Text snapshots only; SOP selection by LLM over a tiny corpus; scripted humans in the evals; a small, friendly mock world.**
8. **Windows only was tested; the web console is a local demo tool** (no login, one run at a time). Not built: S8 (prompt injection), S9 (existing bill), `SESSION_EXPIRY`.

## 12. What I would build next

Short version (full plan in `docs/LIMITATIONS_AND_FUTURE.md`):

0. Close the false-pass gap in code (a procedure names the independent source of a field and requires "a change happened"), a pre-write "any look-alike records?" checkpoint, and a model comparison including a much stronger model.
1. Larger, adversarial eval set and regression tracking per model.
2. Persistent company memory with human-reviewed lessons.
3. Connector SDK and OpenAPI-based tool generation.
4. Durable execution (queue, resume after crash), idempotency keys.
5. Real approval channels (Slack/email) and role-based identities.
6. Vision fallback for UIs without usable DOM.
